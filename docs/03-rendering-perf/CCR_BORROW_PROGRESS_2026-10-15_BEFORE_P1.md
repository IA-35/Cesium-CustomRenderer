## 4. P1：必须按原计划口径判断

原文选定的是 **Hillaire 三张二维 LUT**：T `256×64`、M `32×32`、Sky `192×108`，初始 RGBA16F；不是完整 Bruneton 三维散射 LUT。此前以“完整 Bruneton 未移植”概括 P1 不准确。

当前无 `src/environment/AtmosphereLut143.js`，解析大气仍使用 view × sun 嵌套积分。因此下列事项均未落实：

- T/M/Sky 的 fragment 生成 Pass 与 RHI 资源。
- 介质、半径、模型版本、太阳/相机等真实失效键。
- 仅在成功生成后发布新版本、失败保留旧有效结果。
- 天空查 Sky-view；有限距离使用短 march + T/M 查表。
- 与现有正确基线同参数画面和成本对照。

不需要 WebGPU/compute 或新增三维纹理支持才能开始这个阶段。

- **未完成专项验收**：玻璃、Water、MASK、选中轮廓和 OIT 的新云照明回归；建筑阴影的 texelWorld/级联/bias/Pass 成本本轮未测。

## 7. P4 与资源预算的实际缺口

当前 `VisualPipeline.rebuildRenderGraph()` 的 pooled 接入主要为 AO/Bloom。新云颜色/距离 collection、独立历史、透射率和 resolve 未声明为可追踪的 Graph 资源/Pass。`CloudTemporal143` 直接创建 Cesium Texture/Framebuffer，生命周期已有管理，但不等于 Graph external 绑定完成。

`RenderProfiler143` 当前包住粗粒度 `environment._execute`；纹理枚举仍主要记录环境 noise/raymarch/resolve，**未完整覆盖新云 current、云深度、RGB T、云历史与 medium**。因此不能用其现有小计证明新增内存预算已达标，也没有可靠的云 march/temporal/shadow 分项计时。

资源格式也未达到原预算：云 current/depth/T 等仍以 RGBA32F 为主。云 history 在 half-float 可用时，为 **两张 RGBA16F 颜色 + 两张 RGBA32F 距离/T**：

| viewport；每轴 1/2 history | history 逻辑字节 | 与原约 16 MiB 目标 |
| --- | --- | --- |
| 960×540；480×270 | 6,220,800 B，约 5.93 MiB；浏览器诊断实际记录 | 仅小 fixture，不能代表部署分辨率 |
| 1920×1080；960×540 | 24,883,200 B，约 **23.73 MiB**；按当前格式推算 | history 单独已经超出，尚未计 LUT/current/scratch |
| 3840×2160；1920×1080 | 99,532,800 B，约 94.92 MiB；按当前格式推算 | 需重新设计与实测 |

这些是纹理逻辑存储，不是整卡 VRAM。半浮点颜色不可用时回退 RGBA32F，history 还会更大。RHI 当前具备 RED 的 r16f/r32f 路由；RG16F 没有对应 RG 分配映射，也没有将云深度历史收窄的迁移与 GPU 验收。

## 8. 建议下一步及基线

1. 收口 P0 的雾参数/开关语义，登记当前正确画面、参数、资产与 SDK hash，建立可重复 B2 基线；保留用户已验收的天空结果。
2. 按原计划做 **P1 Hillaire 二维 T/M/Sky LUT**，统一云与天空的辐照度来源；先不以完整 Bruneton 为前置。
3. 将新云 Pass 的 Graph 资源、真实分项计时和完整内存枚举同步补齐；先迁移接口/计量，不在当前视觉阶段宣称性能达标。
4. 收口 P2 的深度/历史存储预算、STBN、连续运动权重和采样优化；准确直射项云影可与 P1/P2 的接入并行规划。
5. 收口 P3 特殊材质回归，再分别推进四层天气和级联云影；获得用户允许进入性能阶段后，按原 §5 的相同条件、3×300 有效帧执行 B2/B3/B4/B5 对比。

旧 `ab-env-on/off` 的数值不能直接作为当前新链路性能。本轮未建立可独立切换/归档的全部 B2/B3/B4/B5 版本，也未测得 environment p95 3–5 ms 或新增资源约 16 MiB 目标。
