# drawcall-report.json 复核

复核对象：`docs/verification/tileset-diagnosis/drawcall-report.json` 及生成脚本 `scripts/diagnose-tileset-drawcalls.cjs`。原报告/脚本/资产未修改。

结论：报告对扫描到的文件提供了可用的 primitive、材质槽和基础三角形清单，但不能作为当前业务的完整 draw call、移动掉帧或 16GB 笔记本内存问题的根因证明。尤其不能据此排除调度/资源处理开销。

## R1 · P1：扫描漏掉业务资源，同时混入未使用的版本和校区

脚本 93–101 行只选取一级目录下直接存在 tileset.json 的目录。实际 `SM_NH_YFL`、`SM_NH_ZHL` 等顶层只有 SN/SW 子目录，因而整组跳过；这些 SW 外壳正在业务默认加载。

直接读取实际 GLB JSON 后确认的遗漏：

| 业务资源 | GLB 数 | primitive 数 | 基础三角形数 |
| --- | ---: | ---: | ---: |
| SM_NH_YFL/SW | 18 | 85 | 1628951 |
| SM_NH_ZHL/SW | 28 | 177 | 1430496 |
| SM_NH_SYL1/SW | 23 | 107 | 1979616 |
| SM_NH_SYL2/SW | 13 | 64 | 1171339 |
| SM_NH_TSG/SW | 5 | 33 | 26492 |
| 合计 | **87** | **466** | **6236894** |

报告同时包含南湖、浑南、Building/BuildingAll 等替代导出，以及与当前公共资源配置不同的 sybm_3dtiles。磁盘存在不等于当前页面同时加载；递归文件扫描也不保证文件被 tileset.json 引用。不能直接把这些总和当作一个业务镜头的负载。indoor/outdoor 均为 0 同样不能证明没有这些内容，分类前已漏掉 SN/SW 根。

建议：以实际业务清单为入口，递归解析 content.uri/url 和外部 tileset 引用；磁盘库存统计另列，标明当前/隐藏/备用/未引用资源。

## R2 · P1：“材质共享率”实际是材质使用覆盖率

脚本 30、43、55 行用 Set 收集被引用的材质索引；169 行计算 `distinctReferencedMaterials / declaredMaterials`。结果 1 表示声明的材质都被用到，并不表示共享程度。

“共享率越低，合批收益越大”（脚本 8 行）没有由这项指标支持。低比值可能只是未使用的材质槽多；去掉未使用材质本身不减少 draw。1075 个 material 定义也不等于 1075 种跨文件不同材质。

建议分开报告引用次数/使用材质数、完整材质状态相同的组、图像内容相同且 sampler 相容的组。纹理共享与几何合批分别评估。本轮独立按嵌入图像原始字节 SHA-256 审计当前南湖清单：834 张图像只有 418 个不同内容，确实存在跨 GLB 复用空间，但这不是 materialSharingRatio 证明的。

## R3 · P1：把 primitive 数直接当运行 draw call，并预先排除调度

脚本 3–4 行直接写“性能瓶颈是 draw call 数量，而不是调度”，但报告没有浏览器帧、CPU/GPU 时间、相机轨迹、可见/加载集合、缓存命中、请求/解码/上传或内存数据。

primitive 数可作资产分段代理指标，不等于实际每帧 WebGL draw：视锥剔除、节点引用、阴影、透明、选中 ID 等通道会改变真实提交数。前述优化实验已经用实际 WebGL 调用确认，选中通道可从 2975 降到 2023，这与离线 primitive 总数不是同一口径。

真实业务引擎基线还观察到约 2.8 万次 Draco 解码调度拒绝前的重复传输副本、约 617MiB 累计复制、加载阶段最长超过 1 秒的帧。新完成的 CPU profile 中直接出现 Cesium 着色器 compile/link 和 compressedTexImage2D 路径。它们不能由离线 primitive 数排除；“是不是主要瓶颈”仍需按加载/移动/稳定阶段分开归因。

## R4 · P2：三角形和 feature ID 的口径不完整

脚本 33–46 行只遍历 mesh 定义，每个 mesh 统计一次，没有计算 scene/node 引用或 EXT_mesh_gpu_instancing 实例数，也没有区分 TRIANGLES/STRIP/FAN/非三角形 primitive mode。14768621 只能按这套有限规则解释，不能称为当前实际提交的三角形量。

例如 SM_NH_Shu 的 27559 是基础网格数；现有实例部件展开后约 17511174 个三角形。植被优化由其他会话负责，本条只是明确统计口径，不介入植被实现。

hasFeatureId 只识别 primitive 的 _FEATURE_ID_0/_BATCHID，漏掉节点级 EXT_instance_features、其他 feature ID 属性及纹理式 feature ID。false 不能作为“没有实例/业务标识，可以安全删掉或合并”的依据。

## R5 · P2：报告不能解释内存压力

文件没有进程私有提交/工作集、JS heap/ArrayBuffer、解码暂存、唯一 GPU 纹理/几何字节、缓存引用和释放周期。材质数/面数不能替代内存分析。

实际处理应分开测加载峰值、转镜头、静止与卸载后的数据；尤其要区分压缩文件大小、解码后 CPU 数据、GPU 分配以及跨 GLB 重复资源。桌面机器上的结果不能直接宣称已通过 16GB/移动 RTX 3060 的验收。

## 可以采纳的部分及后续用法

- 报告对已扫描文件的汇总算术一致：18 组、116 文件、1075 primitive、14768621 基础三角形，未记录解析错误。
- 南湖主建筑 197 个 primitive、地形 70 个，与独立审计吻合，说明材质分段确实值得优化。
- 部分文件只有一个 primitive 却含几十万三角形，说明减少 draw 与减少几何量是两件事，不能只盯合批。
- 后续采用三条并行证据链：当前加载清单的资产结构、移动镜头的真实 CPU/GPU 提交、资源加载/驻留/释放。继续推进已授权的引擎优化，不依据该报告直接丢弃调度与内存工作，也不将离线合批直接当作已验证方案。

源码候选当前仅验证了 Draco 传输副本复用和 JobScheduler 的进度标记/预算修改；尚未替换业务 Cesium。纹理按内容共享仍在实现准备阶段，未计为完成。
