# CCR 性能审查：长帧与瓶颈（2026-10-22，只分析未修改）

基于工作区 main@d3aac33 + 94 个未提交改动。全量测试 1074 项：1069 通过 / 2 失败 / 3 跳过（失败为既有：night-transport 正则未跟上云 LOD 改动；three-r186/TAAUtils.js 参考文件在 three 0.169 下无 getViewPosition 导出）。

## P0 必修
1. 静态阴影签名过重 — src/shadows/ShadowCache.js signature()；调用点 DirectionalShadowPass.js:242。
   每次阴影刷新帧都把所有 caster 的矩阵和 uniform 序列化成数组，做两遍 JSON.stringify，再用 localeCompare 排序。
   本地基准（521 caster，每个 2–8 个 uniform，Xeon 2.8GHz）：每次 13–23 ms，产出 0.3–0.5 MB 字符串。
   - 相机静止时每 3 帧一次（缓存命中也照算）。
   - 相机移动、或车流使缓存失效时，签名必然不匹配，算完照样整图重绘，等于白算。
   - 大字符串进入老生代，推高 major GC（10-20 有一帧 GC 约 58 ms）。
   修法：先做廉价检查（光源 VP、尺寸、caster 数量、revision），不同就直接跳过签名；签名改成数值数组结构比较、复用缓冲区，不用字符串。
2. 车流导致阴影永远不命中 — TrafficSystem.js:212 每个模拟步都调用 invalidate({immediate:false})。
   结果是播放车流时每 3 帧整图重绘 521 个 caster，外加白算一次签名。
   修法：静态/动态阴影分层。静态 caster 缓存成深度图，每次刷新先拷贝静态深度，再只画车辆。
3. 每栋楼一个 DynamicEnvironmentMapManager（Cesium 1.143 默认开启）。
   EnvironmentLighting143.js:388 把 maximumSecondsDifference 设成 60 秒。时钟走动、或时间轴跳变超过 60 秒时，70 个管理器同时重建：
   - 立方体图渲染、卷积、辐照度计算；
   - 每个做一次同步 readPixels（DynamicEnvironmentMapManager.js:823）；
   - 每个 model.resetDrawCommands()，全部绘制命令重建，阴影、TAA 运动记录、shader 查找也跟着失效。
   疑似周期性秒级卡顿的来源（例如 10-20 首次扫描 2549 ms 至今未归因）。需验证：3 分钟内统计 readPixels 次数和 resetDrawCommands 次数。
   修法：整个校园共用一份 IBL/SH，模型传 environmentMapOptions:{enabled:false}；或者放大重建间隔并分帧错开。

## P1
4. ContextDrawDispatcher143._dispatch：每次 draw 都新建 event 对象、3 个闭包和数组；有观察者时还会展开复制 event。
   基准：5 个 handler、1700 次 draw/帧，开销约 1 ms/帧（原生约 0.03 ms）。
   修法：无 handler 时直通原生；复用 event 对象；每帧预先算好颜色帧和目标 framebuffer 等判定；handler 按 pass 预先过滤。
5. BindingScope143：每帧往 WebGL context 对象上添加、再 delete 5 个自有属性（BindingScope143.js:14/18），可能让 gl 对象进入 V8 字典模式，拖慢 Cesium 所有 gl.xxx 调用；这也可能是绑定去重没带来 CPU 收益的原因。
   修法：只安装一次包装函数，用开关控制，不要每帧增删属性。需实测确认。
6. AtmosphereLut143：sky key 的精度到 1 mm 高度、1e-8 太阳余弦（第 37 行），相机高度一变或时间一走就每帧重建 skyView，并且每次调用同步的 gl.getError（第 180 行）和 framebuffer.status。
   修法：放宽量化精度或按变化阈值更新；稳态不调 getError。
7. TAA 下选中轮廓约多出 850 次原生 ID pass 绘制（已知问题）。
8. 冷 shader 编译 45–620 ms：轮廓 ID pass、TAA motion、阴影 cast/receive 等程序都是首次使用时才编译。
   修法：加载阶段做 shader 预热。

## P2
9. 主场景 draw 数约 869：70 个 GLB、444 张图，CPU 主要花在 Cesium 每个 draw 的固定开销上。
   修法：按材质合并网格、压缩贴图到 KTX2。这是结构性最大收益，可降低基础 CPU。
10. EnvironmentLighting.apply 的 key 包含月亮方向，相机移动时每帧都会遍历全部 primitive（白天也是）。
11. EzTree 的 gpuResourceCacheFrames=90：视野外 1.5 秒就销毁资源，转回来时重建，造成跳变和 GPU 缓冲反复创建。
12. PerformanceGovernor 若启用，切换档位会重建阴影图和渲染目标，可能来回抖动。
13. 延迟模式的潜在开销：FrameBridge 对每个命令都新建 frameState/context/RenderItem；SunUniforms 每次 draw 调用同步的 getActiveUniformBlockParameter。
14. RenderGraph.beginFrame 每帧对整个图做 JSON.stringify 求 hash，还生成两份诊断对象。
